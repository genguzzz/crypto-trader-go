# 试运行与回测

回测就是把历史行情按时间顺序重放一遍，让策略**用和实时完全相同的代码**跑一次，看它会发哪些信号、赚还是亏。本系统有两种回测：

| | 试运行 | 回测账户 |
|---|---|---|
| 入口 | 策略编辑器里的 **试运行** 按钮 | 新建账户时选“历史回测”，或策略库里的“用此策略回测” |
| 用什么代码 | 当前草稿（不用发布） | 已发布的版本 |
| 区间 | 最近 N 天，1–60 天，默认 14 天 | 自己选起止时间，最长 365 天 |
| 资金和规则 | 10,000 USDT，默认账户规则（单笔风险 1%、最多 5 个持仓、5 倍杠杆、冷却 30 分钟、必须带止损） | 自己设置 |
| 时间上限 | 90 秒，超时停止 | 后台运行，可以取消 |
| 结果 | 报告、信号（最多 500 条）、交易、运行日志、信号最多的那个合约的 K 线图 | 完整的账户页和回测报告 |
| 保留 | 结果显示完就删除，不留账户 | 一直保留，可以重跑 |

试运行的目的是**快速验证代码能跑、逻辑符合预期**：有没有报错、信号是不是在你以为的地方出现、日志写得对不对。它不足以证明策略能赚钱，14 天太短了。

试运行超过 90 秒会提示“超过 90 秒未跑完，已停止（可缩短天数或减少品种）”。1m、5m 周期 + 多品种最容易超时。

## 回测怎么成交

回测没有历史盘口，用的是“K 线成交模型”：

| 事件 | 怎么成交 |
|---|---|
| 信号下的市价单 | 在**下一根基础 K 线的开盘价**成交，加上半个价差（按 2 bp 价差算）和 1 个最小变动价位的不利滑点。开盘价超出滑点容忍就撤单 |
| 止损 / 止盈 | 用每根基础 K 线的最高、最低价判断是否触发，在触发价成交（加同样的滑点）；开盘就跳空越过时按开盘价 |
| 同一根里止损止盈都碰到 | 按先止损算（保守），除非开盘就越过了止盈 |
| 追踪止损 | 从下一根基础 K 线开始按这根的最高 / 最低价移动 |
| 持仓到期 | 到点后在下一根基础 K 线开盘平仓 |
| 强平 | 按强平价，保证金归零 |
| 手续费 | 按账户设置的 taker 费率（默认 5 bp） |
| 资金费 | 按真实的历史结算费率，每个整点检查 |

**基础 K 线**：策略周期和定时器都不小于 1H 时用 1H K 线回放，否则用 1m K 线。所以一个 4H 策略的信号，是在 4H 收盘后**下一个小时**的开盘价成交。

信号在 K 线收盘时发出，最早也只能在下一根开盘成交，这和实时的情况一致：你不可能在收盘价上成交一个“看到收盘价才做出的决定”。

## 预热和历史数据

策略在 `on_bar` 里读的历史（比如 `ctx.bars(inst, n=150)`）在回测开始时也要有。回放器会预先加载回测起点之前的数据（1m 基础时 3 天，1H 基础时 60 天），读得更早时再按需加载。只要数据库里有，第一根 K 线就能读到足够的历史；数据库里没有，`len(b)` 就会小于你要的数量，所以**一定要判断长度**。

`ctx.bars` 一次最多 1000 根。

## 数据能保留多久

数据库有容量上限，旧数据按合约的“级别”分层删除。和回测关系最大的几张表（默认保留时长）：

| 数据 | 自选 | 活跃监控池 | 最近查看过 | 全市场记录 | 其他 |
|---|---|---|---|---|---|
| 1m K 线 / 持仓量采样 | 30 天 | 7 天 | 7 天 | 2 天 | 不保留 |
| 1H K 线 | 400 天 | 400 天 | 400 天 | 400 天 | 400 天 |
| 资金费结算 | 400 天 | 400 天 | 400 天 | 400 天 | 400 天 |
| 逐笔主动买卖 | 14 天 | 3 天 | 3 天 | 不保留 | 不保留 |
| 交易所主动买卖量 | 90 天 | 30 天 | 30 天 | 7 天 | 3 天 |

空间紧张时还会进一步缩短（系统页能看到实际保留时长）。由此可以推出：

- **1H 及以上周期**的策略可以回测几个月；
- **15m 及以下周期**（或用了小于 1H 的定时器）需要 1m 数据，通常只能回测最近几天到几周；区间里完全没有某个合约的 1m 数据时，回测直接失败：`回测区间内没有 … 的 1m K 线数据`；
- 用 `ctx.series(…, "delta")` 的策略，往前回测时主动买卖数据会越来越稀疏，相应的确认条件会更少触发；
- 用评分（`ctx.rank`、`Screener`）的策略需要回测区间内有整点评分快照；全市场筛选（`Screener(scope="market")`）需要 1H K 线。

## 常见的坑

**看到未来**：在本系统里基本不可能。`ctx` 只返回截至当前时刻**已收盘**的 K 线，评分、资金费、持仓量也都是“截至当时”的。你不需要像在 Excel 里那样小心 `shift(1)`。

**周期对齐**：所有周期按 UTC 对齐。`1D` 是 UTC 0 点到 24 点（北京时间早 8 点到次日 8 点），和交易所 App 里默认按北京时间 0 点划分的日线**不一样**，对不上时先检查这个。`4H` 在 UTC 0、4、8……点收盘。

**缺口**：

- 实时运行时，某个合约某一根 K 线缺数据，这一轮就不会给你这个合约的 `on_bar`。
- `ctx.bars` 返回的数组里缺的那根直接没有，不是 NaN。连续性重要时检查 `b.ts` 的间隔。
- 回测里大周期 K 线由基础 K 线合成，基础数据有缺口时，合成出的那根可能不完整。

**读更细的周期**：1H 基础的回测里也可以调用 `ctx.bars(inst, "15m")`，这些 K 线由 1m 历史合成。但 1m 数据保留得短（见上表），回测区间早于 1m 数据的部分会拿到更少的根数甚至空数组，策略里的长度判断要能应付这种情况，否则回测前段和实时的行为会不一样。

**只看收益**：回测报告里先看交易笔数。几笔交易的收益率没有意义；再看最大回撤，问自己能不能扛住。

**用墙上时钟**：`time.time()`、`datetime.now()` 在回测里是“现在”，不是回放时间。一律用 `ctx.now`。

**全局变量**：回测和实时都是一个独立进程，但重启后全局变量会丢；需要保留的放 `ctx.state`。

## 回测和实时有什么不同

| 项 | 实时 | 回测 / 试运行 |
|---|---|---|
| `ctx.mode` | `"live"` | `"backtest"` |
| AI 审核（执行方式“AI 审核”） | 有 | 跳过，直接进入风控 |
| 人工确认 | 按账户设置 | 跳过 |
| 市价成交 | 按实时盘口逐档吃单，滑点容忍内吃不到的撤销 | 下一根基础 K 线开盘价 + 固定滑点 |
| 止损止盈检查 | 约每 1.5 秒看一次最新价 | 每根基础 K 线的最高 / 最低价 |
| `ctx.notify` | 推送到 Telegram / Webhook | 只写运行日志 |
| `ctx.state` 初始值 | 上次保存的 | 空字典 |
| 信号有效期 | 等 AI / 确认时可能过期 | 立即处理，不会过期 |
| “只记录”执行方式 | 只记录 | 也只记录（回测里不会有成交） |
| 处理函数连续 3 次出错 | 实例暂停 | 回测失败 |

所以回测结果通常比实时**略乐观**：没有盘口冲击，没有 AI 和人工把信号拦下，也没有网络和数据延迟。
