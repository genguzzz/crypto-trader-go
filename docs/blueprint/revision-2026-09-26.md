## 1. 候选池：定稿口径与需要你确认的默认值

```text
eligible  = state=live ∧ settleCcy=USDT ∧ ctType=linear ∧ ruleType≠pre_market
            ∧ instCategory ∈ categories            # 默认全部 {1 加密, 3 股票/ETF, 4 商品}；可配置
turnover12h(inst, m) = Σ volCcyQuote of confirmed 1m bars with open ∈ (m−720min, m]
active(m) = top N of { inst ∈ eligible : window complete ∧ turnover12h > minTurnover }
            ORDER BY turnover12h DESC, instId ASC
```

- 分钟推进：每根全池确认柱到齐（或该分钟截止 +5 s 超时，超时者标 `stale`）后原子计算一次 `active(m)`，发布 `added/removed`。5 s 心跳只推价格和新鲜度。
- 阈值附近抖动：实测当下 ±10% 阈值内只有 5 个币。**不加迟滞改定义**；UI 对刚移出的币保留 `removed` 标记 30 分钟即可。
- 预热：5m 窗口先给出临时名单（标 `provisional`），1m 补齐后转正式；重启从 SQLite 恢复，只补缺口。

**已定（用户 2026-09-26）：默认阈值保持 >1000 万 USDT，上限 N=200 保留为配置项。**实测该口径下池规模约 24–95（中位 52，周末约 40）。备选参考：>300 万约 92、>100 万约 151、第 200 名 12h 仅约 52 万 USDT（均为全类别、当下快照）。

阈值与 N 始终可在配置里改；这里只定默认值。

## 2. 评分：从“预设公式”改为“事实 + 规则 + 战绩”

旧蓝图的问题不在“要不要解释”，而在**把未经验证的因子方向写进默认分**。实测显示直觉方向在短周期上恰好是反的。修订后的三层：

### 2.1 事实面板（I2 必做，无方向假设）

每个币、每个确认分钟输出，全部带单位/窗口/时间戳/新鲜度，并给出**池内分位数**（0–100）便于排序过滤：

| 字段 | 定义（全部仅用 ≤ 决策时刻的已确认数据） |
|---|---|
| `ret_1h/4h/24h` | 永续收盘对数收益 |
| `excess_btc_4h` | 该币 4h 收益 − BTC-USDT-SWAP 同期收益（实测最强单变量，方向待验证） |
| `trend_z_4h` | `ret_4h / (48h 小时波动 × √4)` |
| `oi_chg_1h/4h` | `Δlog(oiCcy)`（币本位，排除价格导致的 `oiUsd` 变化） |
| `vol_surprise_4h` | `log(近 4h quote 成交额 / 过去 7 天同长度中位数)` |
| `funding_hourly` | 当前/上期资金费 ÷ 结算间隔小时数 |
| `basis` | `log(perp/spot)`，无现货映射为 unknown |
| `spread_bps` | 当前 bid/ask 点差（成本 gate 用） |
| `turnover12h`, `rank` | 池口径 |

用户可以按任意字段排序、组合过滤；这本身就满足“多维排序/做多做空过滤”的需求，且不含任何未经验证的断言。

### 2.2 规则（你的“分数”）

- 一个规则 = 版本化 JSON：若干字段的**带符号权重**（对分位数或截断 z 值）+ 硬门槛（点差、数据新鲜度、合约状态）+ 方向（long/short 各自一套）。服务端单一 Go `ScoreEngine` 计算，线上与回放共用。
- 预置 3 个**示例**规则，全部标 `unvalidated`：`trend-oi-confirm`（即旧 v0 的方向）、`short-term-reversal`（`−excess_btc_4h` 为主）、`funding-carry`（资金费方向）。它们是对照组，不是推荐。
- 默认榜单排序 = 你选定的规则；不再有“系统认为的正确分数”。

### 2.3 战绩（让“分数”可证伪，是本次新增的关键功能）

- 录制器每小时对**当时的** active 池、每个启用的规则，记录分数快照（不可改写）。
- 到期后自动计算该规则的**样本外**表现：Rank IC（1h/4h/24h）、top/bottom 五分位的毛/净收益（按快照时刻点差 + 双边 taker 费）、滚动 30 天 t 值、命中率；多重检验提示（同时在看几个规则）。
- 规则详情页显示“自上线以来”的战绩曲线。**只有战绩页数字能支持“这个分有用”的说法**；未达门槛（建议：≥60 天、IC t>2、扣费后价差 >0，且上线后才定义的规则只计上线后样本）时，UI 常显“未验证”。
- 离线研究（`factorstudy` 的正式版）使用同一 `ScoreEngine` 对录制数据回放，保证线上线下一致。

这比旧蓝图的“先设计 v0 公式→再做规则实验室（I3 以后）”更早给出证据，也更贴合“我最看重自己的规则”。

### 2.4 保留不变的原则

多空分别计算不互补；OI 不推断“庄家”方向；解锁/新闻/链上只作风险标签；仓位离场是独立模型（I4）；分数不触发下单。

## 5. 技术选型定稿（依据实测简化）

- **OKX 接入：原生窄 adapter**（`net/http` + `gorilla/websocket`）。实测所需端点只有约 8 个 REST + 5 个 WS 频道，PoC 已在 ~300 行内跑通；第三方 SDK（okx-go 等）不再作为首选，只在需要私有接口签名时对照参考。
- **存储**：`modernc.org/sqlite`（无 CGO）WAL + `goose` 迁移；12h 窗口常驻内存，SQLite 为持久化与图表查询。
- **数值**：原始价格/数量以字符串或定点整数落盘；因子计算用 float64（已声明误差）。
- **前端**：Vue 3 + TS + Lightweight Charts（不变）。
- **本机环境缺口**：当前机器无 Node.js（前端需要）、无 `openspec` CLI（OpenSpec 以手工目录维护，严格校验需安装 CLI）。
